# Chrome ↔ TaleRender Coverage Matrix

**The requirement (user, 2026-11-18):** whatever can be rendered using Chrome must be
renderable in TaleRender, at parity. **Framing (user, 2026-11-17):** TaleRender is a
standalone, full-featured native renderer in its own right; the Tall Tale Shorts skill is
the consumer that can render through either backend (native TaleRender or Chrome). This
matrix is the tracked gap list for that requirement: every Chrome-renderable capability
is a row, and every row carries the evidence for its classification.

**States described.** TaleRender: branch `gpufirst-phase0` at local HEAD `712866b`
(28 commits ahead of main, 0 behind). Production main is `bc12a5c` (the flip binary,
sha256 `24439786…`). Where the two differ, the row says so — the Batch 2 results (brow,
sweat gradation, all DESIGN-CARRY plumbing, the `gpupaint` GPU painter) exist **only on
the branch**; the 19-mood painter and the blink adoption are on both. Chrome side: the
live skill tree, Tall Tale Shorts v7.1.

**Built** 2026-11-18 by a coordinator + 6 seats (face/mood; body/costume; props/scene/
camera; lighting/captions; the Chrome-surface census; verification rows + records audit),
then consolidated: cross-seat duplicates were merged to one canonical row set, orphan
capabilities from the census were grep-verified by the coordinator and rowed, and three
classification disputes were resolved with the reasoning recorded (see *Record
corrections*, §E). Documentation only — no code was changed. No rendered images are in
this document or this repo (programme rule); evidence lives in CI artifacts and in
`~/workspace/talerender-evidence/`.

## How to read this matrix

Gap classes (exactly these seven):

| Class | Meaning |
|---|---|
| PROVEN | Parity measured — the row cites the run or measurement |
| PORTED | Code exists; parity not yet measured end-to-end |
| DESIGN-CARRY | Fields plumbed end-to-end (look/state/loader/`state_key`); painter absent (Batch 2's term) |
| DEFERRED | Absent, but named and sequenced in an existing programme record (a design, a disposition, a scheduled layer) |
| MISSING | Absent — no code, and no design in any record (the row cites the grep that found nothing) |
| SUSPENDED | Blocked on the user's ruling |
| VERIFY-GAP | Renders; a parity measurement is outstanding |

Evidence discipline: a PROVEN row needs a run/doc citation, not a wave record's say-so;
a MISSING row needs grep-backed absence. Where code contradicted a record, the code won
and the disagreement is listed under *Record corrections*. Group 9 rows are
**verification rows** (measurements about the whole pipeline), kept distinct from the
capability rows of Groups 1–8.

A recurring structural fact: TaleRender has **two lanes** — a *film lane* (hardcoded
transcription of the one shipped film, `src/film.rs`) and a *loader lane* (generic scene
files, `src/scenefile.rs`). Coverage differs per lane and rows keep them separate.
Closing the requirement means closing the **generic** lane, not re-proving the film lane.

## The denominator — what "everything Chrome can render" is

There is no separate Chrome painter. The Chrome path executes the project's own page:
`template/src/main.ts` boots fonts → `script.json` + word timings → the three.js engine
→ `buildShots(E)` staging → per-frame `draw(t)`, driven headlessly by
`legacy/chrome-capture/tools/capture.mjs` (7 modes) through the page's `window.OP` API.
The two-skills edition delta (manifest in `~/workspace/two-skills/`) proves the Chrome
and native editions of the skill differ only in the SKILL.md `renderer:` line plus
field edits to 5 tool entries in `library/index.json` — **so the denominator is the
full TS staging/painter surface**, not a Chrome-only subset of it.

  (Tool/sfx/music/example/doc items are not renderer capabilities — see *Exclusions*.)

## Top gaps, ranked by user-visible impact

1. **Sets & set-dressing (Group 5).** 11 of the 14 skill sets have no native builder
   and no scene file (only the Onoda film's jungle/shore/bookshop exist, hardcoded);
   crowd figures, set-piece self-animation, and the 51 `prop3d` pieces ride the same
   transcription programme. Any story not set in Onoda's three places cannot be staged
   natively at all. This is the largest single block of the 66 MISSING rows.
2. **The evaluator / staging layer (Groups 1–2).** Chrome *stages performances* with
   named evaluators — talkTrack/viseme, gaze tracks, the ambient blink family, gait
   styles, gestures, acting performances, move factories, IK, physics paths, springs,
   clip controllers. Rust has the clip evaluator (eval15) and the painter channels, but
   almost none of the named evaluators: staging must arrive hand-expanded. Until this
   layer exists, native coverage means "a bridged film renders", not "the skill can
   stage natively".
3. **Camera staging grammar (Group 6).** The SHOT_CATALOG helpers, the cinema CamClip
   system, and the framing solvers (camForScale/frameSubject/…) have no Rust
   counterpart; the `cameramoves.rs` preset generators exist and are unit-tested but
   are **not compiled into the binary** (no `mod cameramoves;` in main.rs, no caller).
4. **Identity appendages (Groups 1/3).** Wing, ears, hair, flip and bodyPitch are
   DESIGN-CARRY (plumbed, unpainted); tail and scarf-streamer are not even plumbed.
   Two of the four registered characters — Finn the Fox (ears+tail) and Pip the Bird
   (wing) — cannot render their identity appendages; the castsheet parity record lists
   `finn_fox` as blocked.
5. **Environment animation (Group 5).** The whole `envanim.ts` family — rain, snowFall,
   windField/treeSway, waterShimmer/waves, cloudDrift, dayCycle — is absent (only the
   film's fire-flicker formula exists). Weather and within-shot time-of-day cannot move
   natively. All of it is closed-form in t (seek-safe), so this is scope, not
   architecture.
6. **Dizzy (Group 1) — the only SUSPENDED rows.** The TS painter draws a spiral eye
   glyph and treats blink/gaze as inert for dizzy; Rust paints dizzy as a pupil mood
   (all 362 EQ violations in the FACE_TABLE replay are dizzy). Blocked on the user's
   side-by-side ruling (D-5F), not on engineering. No implementation is proposed here.
7. **Verification debts (Group 9).** The fog-chart ≥45 dB PSNR leg has never validly
   run (needs the ×π-amended Chrome re-capture, or a formal user waiver — a named
   remainder of goal `goal_b21124e71eb3`); Gate V's FAIL is a skill-side threshold
   calibration debt (T-29-1), not a renderer defect; the film-s03 golden pin is stale
   against fresh renders by a disclosed, deliberate non-re-pin; the formal PC session
   (determinism E7 + PERF rows on RADV) has never been executed, so every GPU number in
   the record is CI lavapipe. Whole-film A/B vs Chrome is measured (mean 23.02 dB /
   min 19.36 dB, 60 pairs) but was never gated — film-level Chrome parity is therefore
   per-capability (this matrix), not a whole-film pixel claim.
8. **Stamps (Groups 3/8).** The one look item that may close as a formal EXCEPTION
   instead of a port: faithful rendering needs text glyphs (5¢/2¢) inside the painter,
   which the native architecture excludes (text enters as plates). A plate design
   exists (effort L). Needs the user/lead ruling: build it, or record the scoped
   exception — never silently render plain under a stamps look.

## Exclusions — renderable-looking, but not Chrome-renderer capabilities

Named explicitly so the denominator cannot be accused of silently omitting them:

- **All audio** — narration (Kokoro), word timing (Whisper), the 21 SFX syntheses and
  3 music beds (`template/tools/mix.py` et al.), the final mix. The renderer only emits
  cue data and consumes timing data. No pixels.
- **SFX-visual layer: the denominator is zero.** Nothing in the Chrome renderer
  flashes, bursts, or shakes on a cue; cues leave the page as data (`OP.cues()`). The
  only "sparkle" pixels are the awe eye-glint — unrelated to the `sparkle` sound effect.
- **Video encoding & contact-sheet tiling** — in Chrome `video` mode, capture pipes
  JPEG frames to ffmpeg; sheet grids are ffmpeg `tile` outputs. Encode quality is a
  capture/ffmpeg property, not a renderer capability.
- **Native-bridge asset generators** (`text_plates.py`, `prop_plates.py`,
  `poster_stage.py`) exist to feed TaleRender, not Chrome; in Chrome the same texts
  and props are painted live on canvas — the *content* is rowed in Groups 4/8.
- **The native capture adapter** (`capture_native.mjs`, `native_modes/`) is the other
  backend's plumbing inside the same tree — by definition not Chrome surface.
- **QA / lint / planning tools** (registry kind `tool`, 27 items) inspect renders or
  plan films; they paint no film pixels. (The in-page QA trace is executed by the
  Chrome `check` gate but samples rather than renders; its native verdict-role
  counterpart is film telemetry, Group 9.)
- **Publishing metadata** (titles, descriptions, hashtags, thumbnail text) — platform
  metadata, not rendered pixels. There is no renderer-side thumbnail generator in the
  Chrome path beyond the sheet/castsheets rowed in Group 4.
- **Frame-level transitions & letterboxing do not exist on the Chrome side** — grep
  for letterbox/pillarbox over the skill tree: zero hits; the only aspects are 9:16
  (film) and 1920×1080 (sheet board). Nothing to port.
- **Title cards exist on neither side** (grep-backed in both trees). The nearest Chrome
  helper, `bigText` (`core/lib.ts`), has no callers at v7.1 — a defined-but-unused
  helper is not a shipped capability.
- **Underwater bubbles do not exist** — the underwater preset's own comment disclaims
  a bubble system; the registry's `bubbles` item is an audio effect.
- **Storyboard/board text** (`core/board.ts`) is a planning artefact rendered by sheet
  tooling, not in-frame film text.
