## 1. Unit decision: DEGREES

`roll` is in **degrees**, on the camera block and in camera keys.
Stored in Rust as `Camera.roll_deg: f32`; converted exactly once,
`roll_deg.to_radians()`, inside `view_proj` — the same place and
the same call shape as the existing `cam.fov_y_deg.to_radians()`.

Evidence (the format's own conventions, in precedence order):

1. **The camera block's only existing angle is degrees.**
   `docs/scene-format.md` §2: `"fovY": 44, // required, degrees`;
   §14.4 keys carry the same `fovY`. In code: the field is named
   `fov_y_deg` (`scenefile.rs:40`), `cameramoves.rs:92` documents
   its mirror as "Vertical field of view, degrees (the format's
   `fovY`)", and every projection site converts at use:
   `scenefile.rs:1211`, `film.rs:3108`, `ab1.rs:615` all call
   `.to_radians()` on a degrees value. A second angle in the same
   object, in a different unit, would be a standing trap — and a
   keyed segment interpolating `fovY` (deg) and `roll` (rad) side
   by side in one key object would invite exactly the misreading
   the format's exactness laws exist to prevent.
2. **The author-facing source API is degrees too.** The item this
   ruling exists for is authored as `dutch(deg = 5)` (shots.ts:158,
   range 3–7° per `library/cameras.md`); degrees is what a scene
   author writes and what a reviewer reads. `12` in a scene file
   is checkable at sight; `0.20943951606750488` is not.
3. **§11 f32 law is honoured, with its cost named.** Degrees values
   authors actually use are short exact f32s (12 → `12.0` exactly;
   its f32 radian form, computed by the loader, is
   0.20943951606750488). The one transcription cost: the source
   engine's internal `ShotLook.roll` is radians (see counter-
   evidence), so a bridge transcribing a TS-computed roll converts
   rad → deg in f64 and writes the resulting exact f32 degrees —
   one conversion in the bridge, instead of a conversion hidden in
   every reader of every file.

Counter-evidence, considered and rejected (recorded so the lead
can overrule with eyes open):

- **§5 transform ops are radians** ("Ops (angles in radians)").
  That law is scoped to its object: node `transform` lists, which
  mirror three.js `Object3D.rotation` — a different object from
  the camera block, under a different section's heading. Roll does
  not live there.
- **The TS engine's `ShotLook.roll` / `CamState.roll` are radians**
  (shots.ts:28, cinema.ts:73), because they feed three.js
  `rotateZ`, a radian API — while the same engine's camera `fov`
  is degrees (three.js `PerspectiveCamera`), which is precisely
  the split the FORMAT already resolved in favour of degrees for
  its camera data. The format is data, not an API call; it follows
  its own §2 precedent.

If the lead prefers radians for transcription purity, the change
is mechanical (rename the field's semantics, drop the
`.to_radians()`), but it must be decided BEFORE the amendment
lands — the two units differ by 57× and no file can be read both
ways.

## 2. The math (exactly where, exactly what)

One site: `view_proj` (`scenefile.rs:1209` at HEAD), the ONLY
constructor of the scene path's view-projection matrix (callers:
`run_direct` :1331 and `run_composer` :1630 — both paths get roll
from this one change; there is no second vp to keep in sync).

Today: `vp = perspective(fov) * look_at(eye, target, up)`.
Patched, when `roll_deg != 0.0`:

```
view' = math::rotate_z(-roll_deg.to_radians()) * view
vp    = proj * view'
```

(`math::mul(a, b)` applies `b` first, so the rotation acts on
view-space coordinates — a Z-rotation about the view axis, applied
after the look-at basis is built, before projection, as R-A7's
text requires.)

Why the minus sign — derivation, not taste. The source law is
`cam.lookAt(tgt); cam.rotateZ(roll)` (shots.ts `createShoot`).
three.js `rotateZ` post-multiplies the camera's world rotation:
`R' = R · Rz(roll)`. The view rotation is the inverse:
`R'⁻¹ = Rz(roll)⁻¹ · R⁻¹ = Rz(−roll) · V`. Basis form, with
`(x, y, z)` = look-at's (right, true-up, backward) rows and
θ = roll in radians: `right′ = cosθ·x + sinθ·y`,
`up′ = −sinθ·x + cosθ·y`, `back′ = z`. Consequences, all pinned
by the patch's unit tests:

- **Sign:** roll > 0 ⇒ a right-side point's NDC y drops ⇒ the
  horizon tips clockwise, right side down — verbatim the
  `ShotLook.roll` comment (shots.ts:28–31: "roll > 0 rotates the
  camera counter-clockwise around its view axis, so the horizon
  appears to tip clockwise — its right side drops").
- **Centre:** the target lies on the rotation axis ⇒ stays at
  the image centre (geometric identity; in f32 it holds to
  < 1e-6 NDC — the patch's test asserts the geometric form, not
  bit-equality, because the look-at basis dots are themselves
  rounded).
- **Depth/focus:** Rz's third row is (0, 0, 1), so view-space z
  of every point is carried through 0/1 coefficients only — clip
  z and w are bit-identical rolled vs unrolled for the same point
  (asserted in the test). Packed depth, depth ordering and
  `post.bokeh.focus` (a distance along the view axis) cannot
  shift under roll.
- **Image form:** in exact arithmetic the rolled render is the
  unrolled render rotated by roll degrees clockwise about the
  image centre in pixel space (projection scales view x/y by the
  same pixel factor H·f/2, so the view-space rotation survives
  projection undistorted at any aspect).

## 3. Byte-identity argument (absent roll = today's bytes)

The contract's hard clause, met by construction rather than by
approximation:

- Absent `roll` ⇒ `f32_field_or(..., 0.0)` ⇒ `roll_deg == 0.0`.
  Explicit `roll: 0` and `roll: -0.0` land on the same value
  class: Rust/IEEE `==` identifies `-0.0 == 0.0`, so all three
  spellings of "no roll" take the same branch.
- The branch is a **skip**, not an identity multiply:
  `if cam.roll_deg == 0.0 { view } else { mul(rotate_z(..), &view) }`.
  On the no-roll path the patched `view_proj` executes literally
  today's three statements — `perspective`, `look_at`,
  `mul(&proj, &view)` — same functions, same arguments, same
  order, zero additional f32 operations. The output bits are
  therefore today's bits by identity of the op sequence, not by
  a rounding argument.
- Why not multiply by `rotate_z(0)` unconditionally (it is the
  identity matrix: sin_cos(0) = (0, 1) exactly)? Because
  `mul` would still evaluate sums of the form
  `a·1 + b·0 + c·0 + d·0` per element: for finite values that
  returns `a` EXCEPT signed-zero cases (`-0.0 + 0.0 = +0.0`) —
  i.e. bit-identity would rest on "no matrix element is ever
  −0.0", an unproven corpus-wide claim. The branch makes the
  claim unnecessary. (The TS source makes the same choice:
  `if (look.roll) cam.rotateZ(...)` — the branch is the source's
  own additivity mechanism, shots.ts:63.)
- Loader side: parsing adds one `f32_field_or` on a field that is
  absent in every existing file (returns the default without
  touching the value), and `eval_camera_keys` is only called when
  `keys` exist; its added roll read is likewise a fallback read
  on absent data. `Loaded`'s other fields, draw construction and
  both render paths are untouched. The patch's unit test
  `view_proj_no_roll_is_bit_identical_to_the_pre_roll_formula`
  pins the matrix bits (via `to_bits()`) for roll ∈ {0.0, −0.0}.
- Version gate: static `roll` in a **v1** file is a named
  rejection ("camera roll is a format v2 field"), mirroring the
  existing `keys`/`lights` gates — §10/§14's rule that a v1 file
  carrying v2 fields is rejected, not reinterpreted. Key-level
  `roll` inherits the `keys` gate. So no existing v1 file's
  meaning changes, and no v2 file without `roll` changes either.

## 4. Ambiguity found and resolved: keyed-roll interpolation wrap

Angles interpolate ambiguously: keys 350 → 10 could mean +20°
through 0 (short way) or −340° through 180 (long way). RESOLVED:
**plain numeric interpolation, no wrapping, no normalisation** —
`a.roll + (b.roll − a.roll) · u` with the segment's eased `u`,
character-for-character the `fovY` law in the same function.
Reasons: (1) it is the only interpolation law `eval_camera_keys`
has — a second, angle-specific law inside one key object would
be a format surprise; (2) the TS camera blending it mirrors
(`blendCamStates`, cinema.ts) lerps roll as a plain number;
(3) determinism/transcription: the evaluated value stays a
function of the written numbers alone, and an author who wants
the short way writes it explicitly (350 → 370), which reads
honestly in the file; (4) in the catalog's actual range (±7°
dutch) the ambiguity cannot arise. Named cost: a 350 → 10 pair
sweeps the long way — accepted, documented in the amendment text
so no author discovers it from a render. Values are never
clamped: |roll| > 180 is legal data (sin/cos are periodic),
though authors are expected to keep |roll| ≤ 180 for f32
headroom in `to_radians()`.

**Does film.rs construct Camera? NO.** The legacy film path has
its own frame spec (eye/target/fov fields on its own spec type)
and builds its matrices itself — `film.rs:3108–3109`:
`math::perspective(spec.fov.to_radians(), …)` +
`math::look_at(spec.eye, spec.target, [0.0, 1.0, 0.0])`. It never
calls `view_proj`, never constructs `scenefile::Camera`, and the
legacy `--film` staging does not load scene files through
`load_root` for its shots. **Roll cannot leak into the film
path's math** — there is no shared type and no shared function.
(The GENERIC filmseq driver, R1-01, does call `load_root` per
frame — scene files it drives CAN carry roll, which is the
intended surface; the Onoda legacy path and its census are not
that surface.)

**Does telemetry.rs construct Camera? It constructs a DIFFERENT
type**: `telemetry::ProjCamera` (`telemetry.rs:338`, f64
eye/target/up/fov_deg; built in `film.rs:4027` from the film
spec, and in telemetry's own tests :1521/:1585/:1873). This patch
does not touch it, and roll does not leak into it. NAMED GAP for
the lead / R1-02, not a silent one: generic telemetry computes
overflow/continuity boxes via `ProjCamera` with up (0,1,0) and no
roll, so for a future rolled scene the telemetry screen boxes
would be computed un-rolled while the render is rolled. No
current film uses roll, and R-A7's scope is the format +
renderer; if a rolled film ever needs telemetry, `ProjCamera`
gains a roll field and `project_box`'s basis gets the same
Rz factor — flag it in R1-02's line-mapping note.

**Two adjacent surfaces deliberately NOT in this patch** (named
so they aren't mistaken for oversights):

- `cameramoves.rs` `CameraKey` — the authoring mirror of §14.4
  keys ({t, eye, target, fov_y, linear} + `to_json`). It cannot
  EMIT a roll key until it gains a `roll` field. Not needed for
  R-A7 (the dutch item is a static look, and hand-authored scene
  files can write `roll` today); a follow-up if move presets
  ever need to author rolled keys.
- `eval15.rs` §15 clips — camera channels are eye/target/fovY
  only (`channel_kind` :1213–1216; `fold_value` :2311–2317), so
  a clip cannot drive roll after this patch. A `camera.clip`
  fold writes static eye/target/fovY into the document BEFORE
  `load_root` parses it; a static or keyed `roll` written in the
  file survives `process_scene` untouched (the evaluator folds
  only named channels). Adding `camera.roll` (S) to §15.7 is a
  separable evaluator amendment — the scene-format draft
  (insertion 3) says so in the doc itself rather than implying
  the channel exists.
